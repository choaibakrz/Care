# Care · Patient companion

The patient-facing web app is intentionally separate from the staff/admin
console. It is a mobile-first web app for the three-room flow:

- request water, a blanket, a wheelchair or a care-team check-in;
- see the request move through received, assigned, on-the-way and done;
- start an interpreter request without exposing a direct robot command;
- see that listening is off by default and read the urgent-help instructions;
- say how they feel (mood check-in) and ask for a nurse when it is low;
- see today's programme and write questions for the doctor ("My day");
- take a break: guided breathing, a pairs game and generated soothing sounds ("Pause");
- switch between French, English, German, Italian, Spanish and Arabic (right to left);
- connect a room tablet once with a one-time code generated by the admin console;
- personalize the greeting with the first name assigned to that room, without asking the patient for an e-mail address or phone number.

The room and patient-data boundaries are real: the browser calls same-origin
API routes, which use the server-only Supabase secret key after validating the
room-device cookie. Requests, questions, mood check-ins and the daily plan are
scoped to the assigned patient record. The deployed app never calls Supabase,
a robot, or a model service directly. The browser receives only the room label,
the assigned first name and patient-facing content; medical record references
remain in the admin console. The room session is an `HttpOnly`, `SameSite=Lax`
cookie and can be revoked when the patient leaves.

## Run locally

The patient app is served by the Node server used by Google Cloud Run. Run it
from the repository root, not from this directory:

```bash
cd <repository-root>
npm start
```

Open <http://localhost:8080/login.html>. The same server exposes the patient,
room-pairing and admin API routes under `/api`.

## Deploy to Google Cloud Run

Cloud Run uses the root `Dockerfile`. It copies this patient interface together
with the root `api/` routes and starts `node server.js` on port `8080`.

Use these values in Google Cloud Run → **Create service** → **Continuously
deploy from a repository**:

- Repository: `choaibakrz/LeukerBadHack`
- Branch: `^main$`
- Build type: **Dockerfile**
- Build context directory: `/`
- Dockerfile: `Dockerfile`
- Service name: `spectrum`
- Container port: `8080`
- Authentication: allow unauthenticated invocations so room tablets can open the patient page

Add these server environment variables for Preview and Production:

```text
APP_SUPABASE_URL=https://your-project.supabase.co
APP_SUPABASE_PUBLISHABLE_KEY=your-public-publishable-key
APP_SUPABASE_SECRET_KEY=your-server-only-secret-key
SPECTRUM_ADMIN_EMAILS=admin@example.com
```

The public key is not used for room authorization. Never expose the secret key
through a `VITE_*` variable or in a browser bundle.

The patient API contract is available at `/api/openapi.json`. It documents the
same-origin authentication, profile and patient-day routes; it is not a general
proxy to Supabase.

To enable the three-room flow, run `supabase/room_access.sql` and
`supabase/room_patient_data.sql` once in the Supabase SQL Editor. The tables
are inaccessible to browser roles; only the API can read them after validating
an admin token or a room-device cookie.

In Supabase, create the administrator account(s) and set their
`app_metadata.role` to `admin`, or list their email in `SPECTRUM_ADMIN_EMAILS`.
Patient accounts and patient email/phone sign-in are not part of room mode.

Health check: <https://YOUR_CLOUD_RUN_URL/api/healthz> should return HTTP 200.

The public patient URL is the Cloud Run service URL, for example
`https://spectrum-xxxxx.europe-west1.run.app/login.html`.
